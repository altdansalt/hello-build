# 0023 — hello_build ships through its own static registry

## Status

Accepted, 2026-06-11.

## Context

ADR 0019 made skill + module the product, but consumers (fleet ports,
outside users) pin the module with `git_override` at a commit. That
works, yet it is not how the Bazel ecosystem consumes modules: the goal
stated from the start is a BCR module. `git_override` also bypasses
registry resolution semantics entirely, so the consumption path we
validate on every fleet run is not the consumption path we intend to
ship.

Submitting to the actual Bazel Central Registry today would be
premature: the module's API is still moving with every loop iteration,
and BCR submission imposes review latency incompatible with a
fix-per-run cadence.

## Decision

- A static registry at github.com/altdansalt/bazel-registry (served
  raw) carries hello_build releases. Consumers put in `.bazelrc`:
  `common --registry=https://raw.githubusercontent.com/altdansalt/bazel-registry/main`
  followed by `common --registry=https://bcr.bazel.build`, and depend
  with a plain `bazel_dep`.
- `release.sh` cuts a release: tag, `git archive` tarball as the GitHub
  release asset (never the autogenerated `/archive/` URL — those are
  not guaranteed byte-stable), registry entry with sha256 integrity.
- The skill's MODULE template moves from `git_override` to
  `bazel_dep` + registry; the scaffold injects the latest released
  version into PORT_TASK.md and copies SKILL.md from that release tag.
  Fleet runs therefore validate the exact consumption path outside
  users get. `git_override` remains documented as dev-mode for testing
  unreleased tooling, and `local_path_override` stays in
  consumers/hello-standalone (its job is testing the *working tree*).
- A loop iteration that changes `tools/` or MODULE.bazel cuts a patch
  release before the next scaffold — releases are one command, so the
  ADR 0022 rule "a run tests a published version" tightens to "a run
  tests a *released* version".
- Graduation to the real BCR is a future decision, taken when the
  module API stops moving between iterations; the registry layout here
  is BCR's, so the entry transplants as-is.

## Consequences

- The registry repo is a second thing to keep consistent; release.sh
  owns it end-to-end to keep that mechanical.
- Old fleet ports keep their git_override pins (history is honest);
  new ports record the module version they validated.
